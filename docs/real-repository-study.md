# Real-repository comparison protocol: preparation checkpoint

Status: protocol draft, not a preregistered or completed experiment. No model
proposals have been made for these study arms. Freeze the executable budget
controls and grading policy before the first call; changing either requires a
new campaign and retention of the original attempt.

## Question and independent unit

Does enforced memory-pressure feedback produce more verified, transferable
memory improvement than ordinary profiling under a common search allocation?
The independent unit is one fresh model run from the same frozen source, not
an accepted generation or an inner benchmark repetition.

Begin with the qualified archive component, followed by the MochiOS resolver
and a serial, independently graded Worldgame solver workload. Archive results
alone cannot establish generality. The existing archive patch is known and must
not be supplied in prompts, retrieved context or tools for either arm. Use
fresh ephemeral model contexts, not this development conversation. Declare
this prior task exposure in the final report.

## Arms and information

Both arms receive the identical source snapshot, behavioral contract, editable
paths, public tests, ordinary profiling observations, model configuration,
proposal protocol and owner tool access. Final grading is not available for
search. No model may read evaluator policy, private inputs, signing keys,
controller state or the other arm's outputs.

- Scarcity: the same ordinary context plus declared decreasing cgroup memory
  limits and public results under those limits.
- Conventional: a fixed memory ceiling and ordinary measured-peak/profile
  feedback. It keeps profiler access; it is not a deliberately weakened arm.

Pin CPU quota, swap policy, runtime, scratch size, output limit and cache policy.
Archive tmpfs pages consume charged memory; report them as part of the workload,
not as an unexplained allocation effect. A separate-account grader is available;
a separate-host authenticated service is still outside this checkpoint.

## Budget and stopping contract

Use a fixed, seeded schedule of at least two independent runs per arm for an
initial feasibility study, with exactly two allocated proposal slots per run.
This remains a small descriptive pilot. A controller reaching its target must
not silently shorten only one arm: continue the predeclared slots, recording
duplicates and failures, or stop the matched pair and mark it incomplete.
Provider outage, unsupported enforcement, baseline failure and cleanup failure
stop the affected pair. Do not spend leftover budget on extra proposals.

Freeze the same per-call output-token ceiling, per-run input-token allowance,
proposal-call allocation, wall deadline and tool-call allowance for both arms.
The transport must demonstrate enforcement of these limits before launch. The
current CLI transport enforces calls and timeouts, but does not yet enforce
the full shared token allocation; that remains a launch gate. Missing provider
usage is unknown and must not be reconstructed from private reasoning.

Equal limits do not imply equal actual token use or elapsed time. Observed
resource use is an outcome of the assigned method. Report actual input/cache/
output tokens, model time, native trials, tool events and cost where available.
Do not pad prompts, waste calls or truncate only the successful arm merely to
force equal realized totals. A separate token-normalized analysis can report
verified improvement per 1,000 tokens; it does not replace arm-level results.

## Outcomes and grading

Primary feasibility outcomes: final signed correctness verdict and fractional
charged peak-memory change on paired normal-condition transfer. Report latency
regression, severe failures, distinct source hashes and actual search cost.
List every run, including rejected/no-change candidates; do not summarize only
winners. Classify architectural changes using a frozen rubric and independent
review, not the proposing model's own description.

Freeze public and private workload generators, sizes, seeds/tolerance policy,
the minimum useful memory change, latency guard and repetitions before use.
Use fresh hidden inputs once per final lineage, randomized baseline/candidate
transfer order, and identical runtime/CPU/memory/scratch conditions. The native
archive transfer fixture validates this plumbing, including a public-passing
negative control that the sealed gate rejects. Its driver runs in the same
Python interpreter as candidate code, however; it is suitable for the reviewed
candidate and does not establish an adversarial oracle boundary for arbitrary
model code. Address that boundary or explicitly scope and review proposals
before the real-model study.

Interpret two runs per arm descriptively. Meaningful causal claims require a
larger prospective sample, multiple repository components, representative
workload distributions, uncertainty analysis and a practical-effect threshold.
Even a passing signed verdict authorizes no production integration.
